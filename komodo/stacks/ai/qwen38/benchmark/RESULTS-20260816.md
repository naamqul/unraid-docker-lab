# Qwen3.8 Arc benchmark - 2026-08-16

## Outcome

The retained configuration is upstream `llama-server` behind `llama-swap`,
using the full 262,144-token slot, Q6_K weights, the F16 projector, q8_0 K/V
cache, and embedded MTP with `n_max=1`.

The runner remains opt-in under the `qwen38-upstream` Compose profile. The
lightweight proxy can stay running; its model TTL is 600 seconds. The benchmark
did not expose an external API or change Open WebUI automatically.

The conditional B390 phase did not produce a GPU performance result. The
pinned Intel/SYCL build enumerated the GPU correctly, but `llama-server`
reproducibly faulted during model initialization before its health endpoint or
first token. The CPU MTP1 configuration therefore remains the only retained
working configuration.

## Results

All CPU results used the same 262,144-token slot, model, projector, q8_0 K/V
cache, one sequence, 16 threads, fixed corpus/image, and sampling settings.
The retained MTP1 medians combine three text and three vision requests. MTP2
was also repeated to three requests per workload after its first sample looked
faster. The remaining tuning points are one request per workload and are
directional controls.

| Runner | Text TG | Vision TG | Text PP | Vision PP | Text TTFT | Vision TTFT | Text / vision MTP acceptance |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Upstream MTP1, retained (3 runs) | 4.03 tok/s | 4.23 tok/s | 8.20 tok/s | 7.80 tok/s | 44.51 s | 51.83 s | 72.9% / 83.2% |
| Upstream no MTP (1 run) | 3.31 tok/s | 3.30 tok/s | 8.84 tok/s | 8.11 tok/s | 41.27 s | 49.84 s | n/a |
| Upstream MTP2 (3 runs) | 3.83 tok/s | 4.17 tok/s | 7.96 tok/s | 7.39 tok/s | 45.84 s | 54.69 s | 63.3% / 71.4% |
| Upstream MTP3 (1 run) | 3.95 tok/s | 4.39 tok/s | 8.99 tok/s | 8.56 tok/s | 40.59 s | 47.20 s | 50.0% / 59.6% |
| ik_llama MTP1 (1 run) | 3.02 tok/s | 2.98 tok/s | 7.85 tok/s | 6.30 tok/s | 46.52 s | 64.37 s | 65.6% / 69.3% |

Relative to the no-MTP control, retained MTP1 improved median generation by
21.9% for text and 28.1% for vision. Relative to ik_llama MTP1, upstream MTP1
was 33.5% faster for text and 42.2% faster for vision.

The original single MTP2 sample was the fastest of its three samples and did
not represent its median. MTP2 generation ranged from 3.777 to 4.571 tok/s for
text (10.9% sample coefficient of variation) and 4.028 to 4.858 tok/s for
vision (10.2% CV). Its three-run medians were 4.95% slower than MTP1 for text
and 1.36% slower for vision. MTP1 itself ranged from 4.027 to 4.745 tok/s for
text (9.7% CV) and 4.221 to 4.980 tok/s for vision (9.7% CV). MTP2 median
acceptance was also lower: 63.3% text and 71.4% vision, versus 72.9% and 83.2%
for MTP1. The repeated evidence therefore refutes the apparent MTP2 lead and
supports retaining MTP1.

All three retained MTP1 vision responses and all three MTP2 vision responses
passed the fixed color-order check.
The text prompt requested a final marker after a long explanation, but the
model used the entire 512-token cap in its reasoning channel, so the marker
check failed. This was a prompt/output-cap issue rather than a server failure;
use a larger output allowance or disable thinking for short-answer clients.

## OpenVINO NPU result

The exact GGUF did not reach inference on the NPU. These three configurations
were attempted with `GGML_OPENVINO_DEVICE=NPU` and only `/dev/accel/accel0`
mapped into the container:

- 262K with F16 vision projector;
- 262K text-only;
- 131K text-only.

Each exited with code 134 during graph reservation:

```text
pre-allocated tensor (cache_k_l3 (view) (permuted)) in a buffer
(OPENVINO0) that cannot run the operation (PERMUTE)
```

The NPU busy-time counter remained zero and no CPU fallback occurred. This is
a current OpenVINO-backend/model-graph limitation, not a device-exposure,
memory, or projector problem.

## B390 SYCL result

The approved conditional phase stopped Lunar through QGA and moved only the
isolated B390 at `0000:00:02.0` from `vfio-pci` to `xe`. No Unraid restart was
used. `xe.disable_display=1`, FLR remained available, and both
`/dev/dri/card0` and `/dev/dri/renderD128` resolved to the B390. Audio group 16
was not modified by the handoff.

The pinned image was
`ghcr.io/mostlygeek/llama-swap:v250-intel-b10450@sha256:4a28ac2941438751ee129e80861aff83fb77a6e88f7fdb9845ca04eb72e22a25`.
It contains llama.cpp b10450 with the Intel SYCL/Level Zero backend.
`ONEAPI_DEVICE_SELECTOR=level_zero:gpu` exposed exactly `SYCL0: Intel(R) Arc(TM)
B390 GPU`; the CPU was not selectable as a fallback.

Three exact 262,144-context load probes were attempted under the 38 GiB
container cap and 8 GiB host-memory floor:

| Probe | Model layers | F16 projector | MTP | Result |
| --- | --- | --- | --- | --- |
| Intended winner | B390 (`--gpu-layers 99`) | B390/default offload | `n_max=1` | GPF before health/first token |
| Required control | B390 (`--gpu-layers 99`) | B390/default offload | off | Same GPF before health/first token |
| Narrow compatibility probe | B390 (`--gpu-layers 99`) | CPU (`--no-mmproj-offload`) | off | Same GPF before health/first token |

Each process reached model and F16 projector loading, then exited with a Linux
general-protection fault at the same `libc.so.6` offset. llama-swap returned
HTTP 500 with `upstream command exited prematurely`. There was no OOM, memory
guard trip, xe reset, DMAR/IOMMU fault, or CPU fallback. Moving the projector
to CPU and disabling MTP did not change the failure, so no successful fixed
image request, no valid accelerator-activity sample, and no tokens-per-second
number exist for this build. Failure response times are not benchmark results.

The runner was stopped through Komodo and the B390 was restored
`xe -> FLR -> vfio-pci`; the original `xe.disable_display=N` module state was
also restored. Lunar then started normally. QGA, RDP, the B390 at
3840x2160/120 Hz, E428/S90F display audio, and the RZ717 Bluetooth adapter all
passed post-recovery checks. The group-16 lifecycle hook restored and detached
`00:1f.4` at the expected stop/start boundaries, and the post-recovery kernel
fault scan was empty.

## Scope and safety

The server reported exactly one `n_ctx=262144` slot and MTP draft context, with
vision capability active. The measured requests were interactive-size prompts;
the run did not prefill a 32K or 90%-full context. At the observed prompt rate,
those probes would take tens of minutes to hours and were not needed to choose
between the already-separated candidates.

Only one runner was active at a time. An 8 GiB `MemAvailable` guard could stop
only the selected Komodo service. The MTP2 validation recorded 604 one-second
host samples and never fell below 25.3 GiB available; the guard never fired.
Lunar remained running in every CPU/NPU sample with QGA responsive, and no OOM,
DMAR/VFIO, or Intel NPU fault was observed. Lunar was down only for the approved
conditional B390 phase and was fully verified after VFIO restoration.
